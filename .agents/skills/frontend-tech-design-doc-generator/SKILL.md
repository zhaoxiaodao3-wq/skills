# 前端技术设计文档生成器（严格模板驱动）

## 适用场景

当用户希望你基于两份输入文档（PRD + UI设计交付文档）输出 `前端技术设计文档.md` 时，必须使用本技能。

典型触发语句（任一命中即可）：
- 生成前端技术设计文档
- 输出前端技术设计文档.md
- 根据PRD和UI文档生成前端设计文档
- 帮我检查文档是否齐全并生成前端技术方案

## 固定工作流（必须按顺序执行）

1. 接收输入（手动粘贴）
2. 齐全性审查（结构完整性 + 可开发性 + 可验收性）
3. 输出审查报告（分级风险）
4. 生成前端技术设计文档（可追溯、可执行、可验收）
5. 按规则命名并保存到 `docs/`

不要跳步。不要在未做审查前直接生成最终文档。

## 输入约束

用户每次手动粘贴两份文档内容：

- 输入1：产品需求文档（PRD）
- 输入2：UI设计交付文档

若缺任一输入，先要求补齐，不进入生成阶段。

## 字段提取规则

### 从 PRD 必须提取

- 所属项目
- 文档版本
- 最后更新日期
- 当前状态
- 功能清单（建议含编号 Fxxx）
- 业务规则与限制
- 验收标准（建议含编号 ACxxx）
- 非目标范围（Non-Goals）
- 风险与待确认项

### 从 UI 文档必须提取

- Figma正式设计稿链接
- 页面范围
- 页面状态覆盖（至少识别空/加载/错误/禁用/无权限等是否说明）
- 交互关联页面
- 图标库与 Design System 说明（如有）

## 齐全性审查规则（严格）

### 阻塞级（Blocking）

任一命中即判定“不可直接进入开发文档定稿”：
- 无功能清单
- 无验收标准
- 无页面范围
- 无Figma正式链接

### 高风险（High）

- 业务规则关键口径不明确
- 待确认项未闭环且影响接口或交互
- 页面状态覆盖不完整（缺关键状态）

### 中风险（Medium）

- 图标命名/资源入口不统一
- Design System 使用范围不明确

### 低风险（Low）

- 文档描述冗余或组织可优化，但不影响开发推进

## 输出一：齐全性评估报告模板

输出时使用以下结构：

### 1) 审查结论
- 审查结果：通过 / 有条件通过 / 不通过
- 总体风险等级：阻塞 / 高 / 中 / 低

### 2) 已齐全项
- 列出可直接支撑前端实现的要点

### 3) 缺失与风险项（分级）
- 阻塞项：
- 高风险项：
- 中风险项：
- 低风险项：

### 4) 补齐建议
- 每项给出“补充内容 + 责任角色 + 建议时限”

## 输出二：前端技术设计文档结构（固定）

生成文档必须包含以下章节：

1. 文档元信息
2. 背景与目标（现状 -> 问题 -> 可验证目标断言）
3. 本次范围与非目标
4. 前置依赖与阻塞项
5. 总体架构（接口 -> Mapper/Store -> 组件渲染链路）
6. 接口契约与字段映射（标注 Breaking Change）
7. 前端实现要点（组件变更、状态管理、兼容策略）
8. 发布顺序与回滚方案
9. 测试策略与验收清单（尽量映射 AC 编号）
10. 风险与待确认项闭环表（责任人/截止时间/影响）

## 写作约束（必须遵守）

- 不编造：缺失信息明确标记为“待确认”，不要脑补。
- 可追溯：关键结论标注来源（PRD 或 UI 输入段落）。
- 可执行：每节都要有可落地动作，而非空泛描述。
- 可验收：验收项与 PRD 验收标准建立映射。

## 文件命名与保存规则

输出文件保存到：
- `docs/`

文件名必须使用以下格式：
- `{所属项目}-{文档版本}-{最后更新日期}-{当前状态}-前端技术设计文档.md`

命名处理规范：
- 去除文件名非法字符（如 `\/:*?"<>|`）
- 空字段不得省略；若缺失则使用 `待补充` 占位并在报告中提示
- 日期统一保留输入文档原格式；若无则填 `待补充日期`

## 交付时的最终回应格式

完成后必须按以下顺序回复用户：

1. 先给《齐全性评估报告》摘要
2. 再说明已生成的文件路径
3. 最后给出 3-5 条下一步建议（如补齐阻塞项、发起评审、联调准备）

## 失败与回退策略

- 若输入内容过短或结构极度不完整，先输出“最小可用审查报告”，并明确还缺什么。
- 若仅有PRD无UI文档，允许生成“草案版前端技术设计文档”，但必须在文档顶部标注“草案，待UI文档补齐后复核”。
- 若仅有UI无PRD，不生成正式文档，仅输出审查报告与补齐清单。
