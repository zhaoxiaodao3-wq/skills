# 语言可理解度组件开发需求文档

## 一、需求概述
本次提供的3份Figma设计稿链接暂无法直接解析内容，以下需求基于业务逻辑描述整理，所有视觉样式、图表细节、等级标签均以对应设计稿节点为准。组件用于展示课堂语言可理解度的分项占比数据与综合评估等级，包含统计图表、分项指标、总分等级标签、课堂特征描述等核心内容，基于ECharts实现可视化，遵循项目统一的工程化、组件化开发规范，保障可复用性与可扩展性。

## 三、组件状态定义
### 1. 完整数据状态
为组件正常展示态，当语言可理解度相关统计数据可正常获取时渲染，完整展示分项占比、统计图表、总分等级、课堂特征描述等全部模块内容。
### 2. 缺省状态
当核心数据缺失、接口异常无法获取统计数据时，切换展示缺省状态，视觉样式严格对齐缺省设计稿实现，不得自定义缺省样式。

## 四、数据展示规范
### 1. 占比类字段统一规则
- 组件内所有分项占比类数值，统一保留 **1位小数** 展示；
- 若原始值小数位数超过1位，直接截断第2位及后续内容，**不执行四舍五入** 处理。

### 2. 通用字段规则
设计稿中出现的其余所有展示字段、分类标签、辅助文案等，均按设计稿标注的格式与单位直接渲染，不做额外数据转换。

### 3. 三维度分项满分（gauge 刻度）

各维度 arc 进度按 `得分 / 满分` 计算，满分由前端常量固定（接口不返回 maxScore）：

| 维度 key | 展示名称 | 满分 maxScore |
|----------|----------|---------------|
| `vocabulary` | 词汇可理解度 | **35** |
| `syntax` | 句法可理解度 | **35** |
| `content` | 内容可理解度 | **30** |

- 分项 `score` 取值区间：`0 ≤ score ≤ maxScore`（整数展示，Container 层 `Math.trunc` 截断）。
- 综合得分满分 **100**（= 35 + 35 + 30）；汇总区展示 `综合得分 /100`。
- 代码常量：`components/language-comprehensibility/constants.ts` → `COMPREHENSIBILITY_DIMENSIONS[].defaultMaxScore`。

### 4. slice 数据结构（aggregate）

```ts
languageComprehensibility: {
  totalScore: number          // 综合得分，0～100
  dimensions: {
    vocabulary: { score: number, maxScore?: number }  // maxScore 默认 35
    syntax:     { score: number, maxScore?: number }  // maxScore 默认 35
    content:    { score: number, maxScore?: number }  // maxScore 默认 30
  }
}
```

接口预对接时：`vocabulary` / `syntax` / `content` 裸 number 直接映射为 `score`；`maxScore` 由 Adapter 按上表补全（见 api-adapter 需求 §5.5）。

## 五、总分等级映射规则
- 总分计算：各分项 `score` 之和，满分 100（35+35+30）；展示使用 slice.`totalScore` 或分项求和，区间 0～100。
- 根据总分匹配对应等级、课堂特征描述与标签样式，各等级对应关系如下：

| 分数区间 | 等级 | 课堂特征 |
| :--- | :--- | :--- |
| 85-100分 | 卓越 | 语言通俗易懂，学生一听就懂 |
| 70-84分 | 良好 | 语言较通俗，偶有难懂之处 |
| 55-69分 | 中等 | 语言一般，部分学生可能听不懂 |
| 40-54分 | 较弱 | 语言偏学术，学生理解困难 |
| 0-39分 | 薄弱 | 学生基本听不懂 |

- 每个等级对应独立的标签视觉样式，严格对齐「等级标签样式」设计稿实现，不得自定义样式。

## 六、图表实现规范
1.  遵循项目统一技术规范，组件内所有统计图表模块**统一使用 ECharts** 进行实现，不得引入其他图表库。
2.  图表的配色、分项维度、图例样式、提示框、占比数值标注等所有视觉细节，严格对齐设计稿效果。
3.  图表需支持响应式自适应，随容器尺寸变化自动调整布局与尺寸，保证不同屏幕下展示完整、无溢出错位。

## 七、UI与开发通用规范
1.  **组件复用原则**：UI实现优先复用 Element Plus 组件库原生组件，可基于现有组件进行二次样式定制与功能封装，在严格对齐设计稿效果的前提下，最大化复用组件库能力。
2.  **样式隔离要求**：所有自定义样式必须做作用域隔离，仅对当前组件内部生效，不得污染全局样式、不得影响项目内其他页面与组件。样式隔离方案遵循项目现有工程规范。
3.  **响应式适配**：组件需具备完整的响应式适配能力，兼容项目覆盖的主流屏幕尺寸与分辨率，不同视口下布局合理、内容完整展示，无溢出、错位、遮挡、文字截断等视觉异常。
4.  **架构设计**：采用业务逻辑与视图分离的架构设计，结构清晰、职责单一，预留合理的扩展插槽、配置项与钩子，支持后续字段新增、样式调整与功能迭代；所有文件目录划分遵循项目现有前端工程规范，本需求不做强制指定。

## 八、Mock数据方案
开发阶段先行使用Mock数据联调，不依赖真实后端接口，接口就绪后可无缝切换。
1.  Mock数据与业务代码、视图逻辑分离，存放方式遵循项目现有Mock管理规范。
2.  需覆盖以下场景：
    - 全量正常数据场景，覆盖所有分项指标、占比与图表完整展示
    - 缺省状态场景
    - 占比数值含多位小数的截断验证场景
    - 5个等级档位的边界分数场景（如85分、84分、70分、69分等），验证等级匹配逻辑
    - 单分项数据缺失、数据格式异常等边界场景

## 九、开发要求
1.  视觉还原严格对齐Figma设计稿的尺寸、色值、间距、字体与样式细节，全字段完整还原，保证1:1还原效果；
2.  占比数值处理、等级匹配逻辑准确无误，覆盖所有分数区间边界，无计算偏差与等级错配；
3.  图表统一使用ECharts实现，样式与交互符合设计稿要求，支持响应式自适应；
4.  兼容接口异常、字段缺失、数据格式异常等边界场景，缺省状态展示符合设计稿规范；
5.  优先复用 Element Plus 组件库能力，样式严格执行隔离规范，避免全局样式污染；
6.  完成多屏幕响应式适配验证，覆盖项目主流分辨率；
7.  组件设计遵循工程化、组件化规范，具备可扩展性，便于后续迭代维护。
